# ADR-0004: Integración y despliegue continuos

**Date**: 2026-10-29
**Status**: proposed
**Deciders**: Equipo completo (Matías López, Ezequiel Assenza, Nicolás Andino, Lucas Orellana)

## Context

La cátedra va a evaluar la integración y el despliegue continuos. Al cerrar el Sprint 2 el repo tenía un workflow de GitHub Actions que corría build, `go vet`, `gofmt` y los tests en cada PR, pero:
- `main` no estaba protegida: se podía mergear con el CI en rojo o sin aprobación;
- el detector de carreras (`go test -race`) no corría, aunque varias historias tienen tests de pedidos simultáneos y en Windows no se puede usar;
- la cobertura solo se imprimía en el log;
- la aplicación no se desplegaba en ningún lado.

El equipo eligió Render para desplegar.

## Decision

Un solo workflow, [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml), con dos etapas:

1. **CI** (`build-test`), en cada PR a `main` y en cada push a `main`:
   - build, `go vet` y `gofmt`;
   - tests unitarios y BDD **con `-race`**, en una sola corrida que también mide la cobertura;
   - la cobertura queda en el resumen de la corrida y como archivo descargable (`coverage.out` y `coverage.html`).
2. **CD** (`deploy`), solo en push a `main` y **solo si el CI pasó** (`needs: build-test`): llama al *deploy hook* de Render, una URL secreta guardada como el secret `RENDER_DEPLOY_HOOK_URL`. Render compila con `go build` y reinicia el servicio. El job usa el environment `render`, así cada despliegue queda registrado en la pestaña *Deployments* del repo.

**Render** se configura con [`render.yaml`](../../render.yaml), versionado en el repo:
- runtime Go nativo, sin Docker;
- `autoDeploy: false`, para que solo despliegue el pipeline (con el CI en verde) y no cualquier push;
- `/web/proyectos` como chequeo de salud.

`main.go` también termina ordenadamente con `SIGTERM`, la señal con que Render detiene el servidor en cada despliegue.

**Protección de `main`:** exigir PR, una aprobación y el check "Build, vet, fmt y tests" en verde. Es lo que hace que el CI sea una barrera y no solo un aviso.

## Alternatives Considered

### Alternative 1: Docker (imagen en GitHub Container Registry, desplegada en Render)
- **Pros**: el CI prueba exactamente el mismo artefacto que se despliega.
- **Cons**: un archivo más para entender y mantener; Render ya compila Go directamente.
- **Why not chosen**: no aporta lo suficiente para un servicio con un solo binario y sin dependencias de sistema (el driver de SQLite no usa CGO).

### Alternative 2: autodespliegue de Render con cada push a `main`
- **Pros**: no necesita deploy hook ni secret.
- **Cons**: Render despliega aunque el CI esté en rojo, y el despliegue no queda en el pipeline de GitHub.
- **Why not chosen**: el despliegue tiene que depender del CI.

## Consequences

### Positive
- Cada cambio pasa por PR, revisión y CI antes de llegar a `main`, y cada merge se despliega solo.
- Las carreras de datos se detectan en el CI.
- El flujo completo (PR → CI → merge → despliegue) se puede mostrar en la defensa desde GitHub.

### Negative
- En el plan gratuito de Render el disco se borra en cada despliegue: la base SQLite arranca vacía, y el servicio se duerme tras unos minutos sin uso (la primera visita tarda).
- `-race` hace más lentos los tests del CI.

### Risks
- Si el secret no está configurado, el job de despliegue avisa y no despliega (no falla el pipeline). Hay que crearlo al configurar Render.
- Si en algún momento hace falta que los datos sobrevivan a los despliegues, hay que pasar a un disco persistente (plan pago de Render) o a otra base.
